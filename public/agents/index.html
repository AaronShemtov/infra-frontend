/Agentic AI
Architecture

kubectl get deploy -n agents — 3 agents · 3 mcp servers

Three LLM agents that do engineering work on this platform, driven from Telegram: a lead that I talk to, a coder it delegates to, and a reviewer on a different model that cannot write. They reach GitHub, the cluster and Cloudflare only through MCP servers, every tool call they send passes a local policy, and the risky ones wait for me to press a button.

mcp multi-agent human in the loop least privilege opentelemetry genai gitops

The agents run in the agents namespace of the Kubernetes platform and are delivered like every site on it: a Git commit, an arm64 image built in CI, a Flux rollout. An agent is configuration rather than code, and the hard limits (RBAC, the GitHub toolsets, the token's scope) live in Kubernetes objects and server flags kept in Git, outside the model's reach.

Three agents, one codebase

An agent is a YAML profile, not a program: a system prompt, a model, the MCP servers it may use, allowed and denied tools, and its limits. All three run the same Python package from the same image.

reviewerthe lead, as the tool reviewer__askgpt-5.1-codex-maxgithub · clusternone: read-onlyno access20

Delegation

  • The lead hands work over as a tool call.The coder and the reviewer run the same agent loop behind a single MCP tool, ask(task, context). Each call starts a fresh conversation and returns the answer, the number of steps and why it stopped.
  • Over the cluster network, not through Telegram.A Telegram bot never receives another bot's messages. As a tool call, the hand-off also passes the same policy check and lands in the same audit log as everything else.
  • Workers keep no memory and cannot ask a human.A task has to be complete in itself. Anything that needs my button stays with the lead, which is why the coder has no Cloudflare access at all.
  • Small edits stay with the lead.A round trip to the coder costs more than a one-line change, and the lead's prompt says so. It also tells the lead to check the commit itself before reporting what the coder did.

Independent review

  • Every change is sent for review before it is reported done.The lead's instructions say so, for its own changes too and for the small ones: a one-line manifest reaches the live cluster as fast as a large one.
  • A different model from the author.Most code is written by gpt-5.3-codex, and a review by the same model would inherit its blind spots. The choice is about independence, not power.
  • It reads and never writes.Its profile allows read tools by name and denies the common write verbs as a backstop, and its GitHub write mode is read-only. Both limits live in the agent, not in the token, which it shares with the coder. It describes what to fix; it does not fix it.
  • The first line is the verdict.APPROVE or CHANGES REQUESTED, then findings, each with a file and what will break. Only files it actually opened, no invented issues, no style notes. The lead is told to show me the verdict as written.

One credential boundary per pod

Each credential is mounted only in the pods that use it, and only one identity in the namespace has any Kubernetes permissions.

Kubernetes

  • One binding in the namespace.Five Deployments have a ServiceAccount of their own, mcp-github runs as the namespace default, and only mcp-cluster's is bound. Its ClusterRole grants get, list and watch on pods and their logs, events, namespaces, nodes, workloads, jobs and cronjobs, Services and endpoints, ConfigMaps, PVCs, ingresses, gateways and routes. The three agents have no Role or ClusterRole at all.
  • What the role leaves out, on purpose.Secrets, pods/exec, attach and port-forward, every write verb and every wildcard. A change to the cluster is a pull request to the GitOps repository, which Flux applies.

GitHub, Cloudflare and secrets

  • GitHub's own MCP server, self-hosted.Its toolsets are fixed by flags in Git and enforced by the server. On GitHub's hosted endpoint they would be headers sent by the very agent being limited.
  • Read-only GitHub is one commit away.The manifest carries the alternative with --read-only commented out; switching is a commit that Flux applies within about a minute.
  • The Cloudflare token lives in one pod.mcp-cloudflare holds it and never hands it out.
  • Every secret comes from OCI Vault.External Secrets syncs them into the namespace every hour; none is in Git. The GitHub token is fine-grained and limited to the repositories the agents work in, and the lead has a Telegram bot of its own, separate from the AI SRE agent's.

04 ·

Local policy and human approval

Two layers decide every tool call an agent sends, before it goes out. The profile decides which tools the model sees at all; the policy reads the call's arguments and answers allow, deny or ask me. Each agent also has a GitHub write mode in its ConfigMap: direct push for the lead and the coder, read-only for the reviewer, and a pull-requests-only mode in between. Web search is the one exception to all of this: Azure runs it on its own side, so it never reaches the policy.

  1. modelproposes a tool call with its arguments
  2. profilea tool outside the profile was never offered; github__delete_* is denied to all three
  3. policyreads the arguments: allow, deny, or ask
  4. methe tool and every argument in Telegram, with two buttons: run or reject
  5. resultit runs, or the model is told why not and that this is a decision, not an error
the calldecisionwhy
a read: get_, list_, search_, read_, describe_ …runsA tool counts as a read if its name starts with a read verb, or if it is one of two GitHub read tools listed by name. Any other name is treated as a write.
a branch or a pull request in the GitOps reporunsA pull request has a diff a person can read.
merging that pull requestasks meFlux applies the merged branch to the live cluster within minutes.
any other write to the GitOps repo's main branchrefusedWhatever the write mode, the policy refuses it: a change to the cluster goes through a pull request.
a write to another repositoryrunsIn direct-push mode. A bad commit can be reverted, and the lead's instructions send it to the reviewer before the work is reported done.
a Cloudflare write: DNS, WAF, tunnel, cacheasks meA deleted DNS record takes a site offline until someone notices.
a write to the clusterrefusedThe cluster changes through Git only. The refusal says so and points to a pull request; the ClusterRole could not do it anyway.
a task for the coderasks meThe policy has no rule of its own for the coder's server, and a server without one is gated rather than guessed.
a reviewrunsThe reviewer cannot change anything, and a review that costs a button press is a review that gets skipped.
remembering or forgetting a factrunsThe agent's own two tables; a wrong fact is easy to see and drop (see Memory).

How approval works

  • The loop simply waits.When the policy says "ask", the turn awaits a callback. The Telegram layer posts the tool and its complete arguments with the two buttons, and the press resolves the wait. The whole turn stays one coroutine, with no pending state to store and resume.
  • Silence is a no.No answer within ten minutes counts as a rejection. The allow-list is checked again on the press, because anyone who can see the message can press the button.
  • A refusal is a decision, not a failure.Every policy refusal reaches the model as "denied by local policy". The lead's prompt tells it not to retry or look for a way around, but to explain and offer a path that is allowed; a worker reports the refusal in its answer.

Who can ask, and who can be asked

  • Workers have nobody to ask.In the coder and the reviewer, a call that needs approval is refused with a reason of its own, so the worker finishes and lists what still needs confirming, and the lead asks me.
  • A fail-closed allow-list.The bot answers listed Telegram users only. An empty list would refuse everyone, so the process refuses to start with one.
  • A button press gets through mid-turn.Updates are handled concurrently, so an approval or /cancel is not queued behind the turn it is meant to affect, and a new message is turned away while a turn runs.
05 ·

One request, end to end

A turn is a loop: call the model, run the tool calls it asked for, feed the results back, until it answers without one. Every way out of the loop has a name.

  1. The message passes the allow-list. The system prompt is the profile's prompt plus the facts stored about me.
  2. Earlier history in the lead's chat is trimmed to its 120k-token context budget, by whole turns and four turns at a time: a tool result never loses the call that asked for it, and the start of the prompt stays stable, so the provider's prompt cache keeps hitting. The current turn is always sent whole, and the coder and the reviewer start every task fresh.
  3. The model answers. Each tool call it makes goes through the policy and runs on its MCP server, with a two-minute timeout, or fifteen for a task delegated to the coder.
  4. Each result is clipped to 12,000 characters before it enters the transcript, because tool output is sent again as input on every later step.
  5. The answer goes back with a short usage footer: model, steps, the stop reason, tokens with the cache hit rate, and the number of tool calls with their total time.
stopped_becausewhen
completedThe model answered without asking for a tool.
max_stepsThe step limit: 30 for the lead, 40 for the coder, 20 for the reviewer.
token_budgetThe turn's billable tokens, uncached input plus output, passed the ceiling: 300k for the lead and the reviewer, 500k for the coder. A backstop against a pathological turn, not a limit ordinary work meets.
cancelled/cancel, checked between steps.
model_output_limitThe model hit its own output limit. A tool call that may have been cut short is never run.
llm_errorThe model call failed; the error type is counted in the metrics.
The turn loop — ai-agents-platform/src/agentcore/loop.py (abridged, comments added)
while steps < self.max_steps:
    if cancel is not None and cancel.is_set():
        stopped = "cancelled"; break
    if usage.billable > self.max_billable:        # uncached input + output
        stopped = "token_budget"; break
    steps += 1
    messages = chat.transcript(system_prompt, max_tokens=token_budget)
    response = await self._llm.complete(model=model, messages=messages, tools=catalog.specs or None)
    usage = usage + response.usage
    if response.finish_reason == "length":        # never run a truncated call
        stopped = "model_output_limit"; break
    if not response.tool_calls:
        stopped = "completed"; break
    for call in response.tool_calls:              # policy, approval, MCP call, audit line
        result_text, called, ms = await self._execute(call, ...)
        chat.append({"role": "tool", "tool_call_id": call.id, "content": _clip(result_text)})
else:
    stopped = "max_steps"
06 ·

MCP servers

Three tool servers, each its own Deployment. The cluster and Cloudflare servers are written for this platform on a shared skeleton. The coder and the reviewer sit on the same skeleton, because the lead calls them over MCP like any other tool server. The GitHub server is GitHub's own image.

The in-house servers

  • MCP SDK 2.x over Streamable HTTP, stateless.The servers keep no session state, so one can restart or scale while an agent is working. The client opens a fresh MCP session per call and keeps only the HTTP connection pool alive.
  • Health that means something./healthz for liveness, a /readyz that checks the upstream, and a /metrics endpoint; section 09 says which ones are scraped.
  • Errors the model can act on.A tool returns {ok: false, error, hint} instead of raising, so the model reads one short line it can act on rather than a stack trace.

On the agent's side

  • Namespaced tool names.server__tool, so two servers can share a tool name and a profile can address a whole server as github__*.
  • Inside the model API's limits.Tool descriptions are cut to 1,024 characters and names to 64. GitHub's server ships longer descriptions, and a single one over the limit fails the whole request.
  • Header-bound parameters.GitHub's server marks owner and repo with x-mcp-header, and the client echoes them as Mcp-Param-* headers, so a gateway could see which repository a call touches without parsing the body.
CLUSTER

mcp-cluster — six read-only tools

own code · its own ServiceAccount with a get/list/watch ClusterRole · holds no secret
  • list_namespaces and list_pods: phase, ready containers, restarts, node, waiting reasons and images, with a filter for unhealthy pods only.
  • get_pod_logs: a tail of 1 to 500 lines, including the previous container after a crash.
  • list_events: up to 100 events, newest last, each message cut to 300 characters.
  • get_deployment and get_service: replicas, strategy, images and conditions; ports and up to 20 endpoints.

Every answer is a summary, not the raw object. A pod is several kilobytes of JSON that is almost all irrelevant to why it is unhealthy, and ten of them would push the conversation out of the context window. There are no write tools, and none could work: the ServiceAccount has no write verb.

CLOUDFLARE

mcp-cloudflare — fourteen tools written for this platform

own code · the only holder of the Cloudflare token · every write the lead makes asks me first

Cloudflare's official MCP servers run only on Workers, and the hosted ones do not cover DNS records, WAF rules or tunnel configuration. So this one wraps the REST calls actually needed, named by the verb convention the policy keys off.

  • 5 reads: list_zones, list_dns_records, list_waf_rules, list_tunnels, get_tunnel_config.
  • 9 writes: create, update and delete for DNS records and for WAF rules, add_tunnel_hostname, update_tunnel_config, purge_cache.

Two things that break if done naively

  • Tunnel ingress is ordered and ends in a catch-all. A hostname appended after it would never match, so new rules go in front of it. The configuration is replaced as a whole on every change: add_tunnel_hostname reads it, inserts the rule and writes it back, and update_tunnel_config refuses a list that does not end in the catch-all.
  • WAF custom rules live in the Rulesets API. They sit in the entrypoint ruleset of the http_request_firewall_custom phase, and changing one rule means putting the whole list back. Actions are checked against an allow-list first.

A cache purge takes up to 30 full URLs per call and cannot be mixed with "purge everything".

ai-agents-platform/src/mcp_cloudflare/tools.py (abridged)
def insert_before_catchall(ingress, new_rule):
    rules = [r for r in ingress if not is_catch_all(r)]
    tail = [r for r in ingress if is_catch_all(r)]
    rules.append(new_rule)
    # A config with no catch-all is invalid; supply one rather than PUTting a broken config.
    if not tail:
        tail = [{"service": CATCH_ALL_SERVICE}]
    return rules + tail[:1]
GITHUB

mcp-github — GitHub's official server, self-hosted

GitHub's github-mcp-server image, v1.11.0 · toolsets fixed in Git · holds no credential
  • Five toolsets: repos, issues, pull_requests, git and context. That list is the ceiling on what any agent talking to this pod can do.
  • No credential of its own. In HTTP mode the server takes Authorization: Bearer from each request, so the GitHub token stays in the agent pods and travels with every call.
  • A TCP probe rather than an HTTP one: an unauthenticated request is answered with 401.
  • Pinned on purpose. The image is not under Flux image automation; a new version is a deliberate commit.

Models on Azure AI Foundry

One client for both of Azure's APIs, Chat Completions and Responses. Which model uses which is configuration, and before I make a model the default I check it on its endpoint.

modelroleAPI
gpt-5.6-lunathe lead's default; /model switches a chat to another model from an allow-listResponses, with web search hosted by Azure
gpt-5.3-codexthe coderResponses only
gpt-5.1-codex-maxthe reviewerResponses only

One client

  • The plain OpenAI SDK against the Foundry v1 endpoint.No api-version, and the deployment name goes in the model field, so switching the lead's model is a ConfigMap edit, not a release; the coder and the reviewer pin theirs in their profiles. The provider sits behind a one-method interface, so another one would change a file, not the loop.
  • The endpoint is configuration, not a guess.The codex models answer only on /responses, and hosted web search exists only there. A list in the ConfigMap says which deployments use it; the model's name never decides.
  • Reasoning is carried between steps.A Responses model returns reasoning items with its tool calls. They are replayed verbatim on the next request and stripped before anything goes to /chat/completions, so /model can move a chat between the two APIs mid-conversation.
  • Usage counts what is billed.Input, output, cached and reasoning tokens are tracked apart. The turn's ceiling counts uncached input plus output, because the cached prefix sent again on every step is billed at a fraction.

Chosen by measurement, checked by hand

  • The coder's model was picked on a real task.On the same Dockerfile task gpt-5.3-codex answered in 4.0 s against 31.8 s for gpt-5.6-sol, and caught the readOnlyRootFilesystem requirement that gpt-5-mini missed.
  • A preflight command, run before the default changes.python -m agentcore.preflight <model> replays the recent history of the longest stored conversation, asks a question only a tool can answer, and reads a live web page, which must show a web_search_call. It exits 0 only if nothing failed, so it could gate a pipeline; today I run it by hand.
  • Why those three checks.The endpoint a model is routed to decides which capabilities exist, and "does it answer?" tests none of them. A model can reply fluently and still reject the stored history, never call a tool, or answer from memory instead of reading the page.
08 ·

Memory without a volume

The agents get no persistent volume: the cluster's Always Free block storage goes to Prometheus. So the lead keeps its history and what it knows about me in the Autonomous Database the URL shortener already uses, in a schema of its own.

Where it lives

  • Same database, separate schema.The schema has no grants on the shortener's data, so an agent holding its own password cannot read or drop another application's table.
  • Plain HTTPS, no driver.ORDS REST-Enabled SQL with Basic Auth: no Oracle client library and no wallet in the image.
  • Two tables.conversations, one row per message, read back through an index on (agent, chat_id, id) that finds the newest N for a chat without a sort; and facts, a key and a sentence each.
  • Each write commits itself.One PL/SQL block per write, and a fact is upserted with a single MERGE, so two concurrent writes cannot race a read-then-write.

How it behaves

  • History survives a restart.The first message after a restart reloads the newest 40 messages, cut back to a clean turn boundary: no tool result without its call, no call without its result.
  • Facts have tools of their own.memory__remember and memory__forget run inside the agent and pass the same tool catalogue, allow and deny patterns and policy as any MCP tool. /memories lists the stored facts and /forget drops one.
  • It degrades, except where that would mislead.A lost history write is logged and the turn goes on. A failed fact write is reported, so the agent never claims to remember what it did not store.

Metrics and audit

The agents are measured like any other service on the platform, and no message text reaches a metric: the metrics count, and the audit log keeps a hash of each call's arguments instead of the arguments. Everything lands in the monitoring stack described on the platform page.

metricwhat it measures
gen_ai_client_token_usageTokens per model call, by type: input, output, cached, reasoning.
gen_ai_client_operation_duration_secondsModel call latency, with the error type when a call failed.
gen_ai_invoke_agent_*One turn: how long it took, how many model calls and how many tool calls.

Metrics

  • OpenTelemetry GenAI names, as specified.Metric names, units and the token and model-call buckets come from the conventions, so any GenAI observability tool can read them without re-instrumenting. Two token types, cached and reasoning, are added because the spec has nowhere to put them. The conventions are still marked Development, so the code follows the spec's spelling and expects churn.
  • Own names only where the standard has none.Policy decisions, approvals and the time a person takes get the agent_ prefix, so the two sets never look like one.
  • Bounded cardinality.The tool name comes from the model, which can invent one. The label keeps at most 128 distinct values; the rest become other.
  • Scraped like everything else.A ServiceMonitor scrapes the lead and the coder every 30 seconds; the reviewer is not scraped yet. The MCP servers' CPU and memory already come from cAdvisor.

Dashboard and audit

  • The AI Agents dashboard asks five questions.What it cost, how much it did, where the time went, what was refused and what failed. The top row includes "Waiting on a human, p95".
  • Azure's side of the story.Azure Monitor panels show what the client cannot see: throttling, tokens per deployment, server-side latency and content-filter refusals. A service principal with Monitoring Reader on that one resource reads them; metrics only, no exporter pod.
  • One audit line per tool call.JSON on stdout, collected into Loki: agent, tool, decision, result, duration, the argument names and a hash of the arguments, never the arguments themselves, which routinely carry whole files. A failed call keeps the start of its error message.
  • Secrets are masked by their shape.In the agent processes, a filter on the standard log handlers masks bot tokens, GitHub tokens, bearer and API-key headers and credentials in URLs before a line is written, and the chattiest HTTP clients log warnings only.

10 ·

Build and delivery

The same path as every service on the platform: a commit, a native arm64 build, a Flux rollout. Nothing is built or deployed by hand.

Image and CI

  • One image, several entrypoints.The agents and both in-house MCP servers share one set of dependencies, so five Deployments run one image and differ only by command: one pipeline, one registry repository, one image policy.
  • Checked before it is built.ruff; an import of the lead's and both MCP servers' entrypoints, which is where a name that moved in the MCP SDK breaks first; then pytest across 29 test files. On a pull request the pipeline ends here; only main is built and pushed.
  • Built natively for arm64.The nodes are Ampere A1, and the image is built on GitHub's arm64 runner, with no emulation. It is pushed to OCIR, Oracle's container registry, tagged 0.0.<run> and with the short commit SHA.
  • Small and unprivileged.A two-stage python:3.12-slim build: only the virtual environment reaches the runtime image, which runs as UID 10001 and carries the agent profiles as data.

Rollout and runtime

  • Flux rolls it out.Image automation picks the newest tag and commits the bump to the GitOps repository. CI posts each build and Flux each rollout to t.me/onemsplatform.
  • Restricted pods.Non-root, seccomp RuntimeDefault, no privilege escalation, a read-only root filesystem and all capabilities dropped. The only writable path is an emptyDir at /tmp, and mcp-github has none at all.
  • One poller per bot token.Telegram allows a single long-polling client per token, so the lead uses the Recreate strategy: the old pod stops before the new one starts.
  • Readiness checks the real dependency.The lead is Ready only while its Telegram poller is running; mcp-cluster only while it can list namespaces through the API server, so broken RBAC shows up as NotReady; mcp-cloudflare only while Cloudflare accepts its token.

Decisions and trade-offs

Why it is built this way, and what that costs.

Decisions

  • Credentials are split by podnot by repository and not by prompt. The agents hold no cluster role and no Cloudflare token; mcp-cluster has the only RBAC binding and mcp-cloudflare the only Cloudflare token, and the GitHub token travels from the agents to mcp-github with each request.
  • Delegation over MCP, not a protocol of my ownthe lead uses one interface for infrastructure tools and for other agents, and every hand-off is checked and logged the same way.
  • Gate rather than guessa tool whose name is not a read verb counts as a write, and a server the policy has no rule for asks first instead of being trusted.
  • Reuse GitHub's server, write Cloudflare'sGitHub's official image can be self-hosted and pinned; Cloudflare's could not be self-hosted and did not cover what was needed.
  • Memory as two in-process tools, not another serveranother server would mean another Deployment, another copy of the database password and a network hop to a table the agent can already write.
  • Standard metric names firstthe dashboards stay portable, and only what the convention cannot express gets a name of its own.

Known limits, accepted for now

  • A pending approval does not survive a restart.It lives in the coroutine that waits for it, so a rollout in the middle of an approval drops it and the request has to be repeated. A durable approval store is the next step.
  • Single replicas.A rollout of the lead leaves a short gap while the new pod starts, and a worker that restarts drops the task it was running.
  • No alerts on the agent metrics yet.They are watched on the dashboard only.
  • Facts are loaded whole.Fine while they are few; past that, search over facts and history, since the database supports vectors.
  • Some rules live only in the policy.Approvals, the reviewer's read-only mode and the rule against pushing to the GitOps repository's main branch are enforced inside the agent. RBAC, the GitHub toolsets and the token's repository scope bound everything else from outside it.
