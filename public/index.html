Infrastructure Walkthrough

The platform behind 1ms.my, cv.1ms.my and this page

  • 1ms.my
  • cv.1ms.my
  • github.com/AaronShemtov

This page documents the production-grade Kubernetes platform that serves 1ms.my (URL shortener), cv.1ms.my (CV), and the page you're reading now (infra.1ms.my). The whole stack runs on Oracle Cloud Always Free tier at €0/month and is operated entirely through GitOps from public GitHub repositories — no manual kubectl apply against the cluster.

It exists to mirror real-world DevOps practice: multi-app Kubernetes platform, automated image promotion, secrets sourced from a managed vault, no public load balancer, no static credentials, no kubeconfig drift.

Architecture

Cloud platform — Oracle Cloud (OCI)

Region: il-jerusalem-1 · Always Free tier

▼

The whole platform runs in OCI region Israel Central (Jerusalem) — the home region of the tenancy. Always Free quotas cover everything currently deployed. Storage in OCIR is technically pay-per-GB, but on this scale rounds to ~€0.01/month.

  • Compute — 4 OCPU + 24 GB RAM Ampere A1 (Arm), fully allocated to the OKE worker pool.
  • Block Volume — 200 GB total Always Free; currently consumed by three node boot volumes (~47 GB each).
  • Container Engine (OKE) — managed Kubernetes control plane; the cluster itself is free, only the worker nodes count against compute quota.
  • Container Registry (OCIR) — private repos for backend, frontend, cv, infra images.
  • Vault + Secrets — master encryption keys (software) + tenancy secrets, sourced by ESO into Kubernetes Secrets at runtime.
  • Autonomous Database — JSON workload type, 1 ECPU + 20 GB, SODA REST API endpoint.
  • Identity — Dynamic Groups + Policies grant OKE worker node identities access to Vault secrets and ADB without any static credentials.

Kubernetes — OKE cluster

v1.32.1 · 3 worker nodes · VCN-Native CNI · OCI Block CSI

▼

Three worker nodes, intentionally uneven in shape:

  • 10.0.1.37 — 1 OCPU / 6 GB RAM — application pods (writer / reader / frontends / cloudflared).
  • 10.0.1.66 — 1 OCPU / 6 GB RAM — sister node to .37; pod anti-affinity spreads replicas across them for HA during rolling updates.
  • 10.0.1.135 — 2 OCPU / 12 GB RAM — reserved for the observability stack (Prometheus / Grafana / Loki). Currently underused; will host the monitoring HelmReleases when that work lands.

The split exists because the Ampere A1 Always Free pool is 4 OCPU + 24 GB total. A 2+1+1 split gives one "fat" node for observability (memory-heavy) while keeping two lighter app nodes whose loss is absorbed by anti-affinity-spread replicas.

Security baseline: every namespace enforces the restricted PodSecurityStandard — non-root, no host networking, dropped capabilities, RuntimeDefault seccomp profile, read-only root filesystem where the workload allows.

Networking & Ingress

Envoy Gateway (Gateway API) · ClusterIP service · no public LB

▼

There is no public OCI Load Balancer. The single Always Free LB slot is reserved; the cluster has no public IP and no inbound firewall holes.

Envoy Gateway 1.x runs the data plane, configured with an EnvoyProxy CR that pins the Envoy Service to ClusterIP (overriding Envoy Gateway's default LoadBalancer behavior). A single Gateway resource has one HTTP listener on port 80; allowedRoutes.namespaces.from: All lets HTTPRoutes from any application namespace attach without ReferenceGrants.

Routing is hostname-based — one HTTPRoute per site:

  • 1ms.my → urlshortener namespace (writer / reader / frontend by path)
  • cv.1ms.my → cv namespace (cv-frontend)
  • infra.1ms.my → infra namespace (this page)

External traffic reaches Envoy via Cloudflare Tunnel — see the next section.

Cloudflare — Registrar, DNS, Tunnel, Proxy

homelab-tunnel · 4 cloudflared connectors · orange-cloud proxied

▼
  • Registrar — the 1ms.my domain is registered through Cloudflare Registrar (at-cost renewal, no separate registrar bill).
  • DNS — zone 1ms.my hosted on Cloudflare. Records for 1ms.my, cv.1ms.my and infra.1ms.my are CNAMEs pointing at the homelab tunnel; Cloudflare creates these automatically when public hostnames are added to the tunnel.
  • Proxied (orange cloud) — all traffic terminates TLS at Cloudflare's edge. That gives free TLS certs (auto-renewed), DDoS protection, edge caching of static assets (CSS, JS, images, PDFs), and analytics.
  • Cloudflare Tunnel — cloudflared Deployment with 2 replicas inside the cluster establishes outbound TLS connections to Cloudflare's edge. No inbound ports open on OCI; the cluster has no public IP. The tunnel is HEALTHY with 4 connectors across Tel Aviv and Marseille edge POPs.
  • Public hostnames in the tunnel route each site to the Envoy data-plane Service via in-cluster DNS over HTTPS (No TLS Verify because Envoy serves a self-signed internal cert).

GitOps with Flux

Flux v2.6.4 · 6 controllers · Image Automation closes the loop

▼

Six Flux controllers in the flux-system namespace: source-controller, kustomize-controller, helm-controller, notification-controller, image-reflector-controller, image-automation-controller.

Two root Kustomizations split the cluster into a base infrastructure layer and an application layer:

  • infrastructure — applies ./infrastructure/ (Gateway API CRDs, Envoy Gateway, External Secrets Operator, cloudflared, image-automation pipeline, metrics-server).
  • applications — applies ./applications/ (urlshortener, cv, infra). Depends on infrastructure being reconciled first.

The Git source uses SSH with a write-enabled deploy key — the same key Flux uses to pull manifests is reused to push tag updates from Image Automation. No personal access tokens, no expiration.

Image Automation loop:

  1. Push to urlshortener-backend (or any source repo) → GitHub Actions builds image, tags :0.0.<run_number> + :<sha> + :latest, pushes to OCIR.
  2. ImageRepository scans OCIR every 2 minutes.
  3. ImagePolicy picks the highest tag matching semver range >=0.0.0.
  4. ImageUpdateAutomation finds Deployment YAMLs containing the marker # {"$imagepolicy": "flux-system:<policy>"}, edits the tag, commits to personal-k8s as the "Flux Image Automation" author.
  5. kustomize-controller picks up the new commit, applies; rolling update kicks in.

End-to-end: git push in a service repo → new pods running ≈3 minutes later, with no manual intervention.

CI/CD & Container Registry

GitHub Actions · OCIR · linux/arm64 only

▼

Each source repo has its own GitHub Actions workflow:

  • actions/checkout@v4
  • docker/setup-qemu-action + docker/setup-buildx-action — Buildx for cross-arch builds.
  • docker/login-action with OCIR token stored in OCIR_AUTH_TOKEN repo secret.
  • docker/build-push-action@v6 with cache-from/cache-to: type=gha for layer reuse.

Builds target linux/arm64 only — matches the Ampere A1 node arch, avoids slow QEMU emulation when pulling. The build itself runs natively on amd64 (Buildx --platform=$BUILDPLATFORM), only the binary is cross-compiled.

Why GitHub Actions and not OCI DevOps? OCI DevOps service is free, but its build runners consume OCPU hours against the same Ampere A1 pool that's already 100% allocated to OKE. GitHub Actions is unlimited free for public repos.

Secrets management

External Secrets Operator · OCI Vault · Instance Principal auth

▼

External Secrets Operator (ESO) reconciles Kubernetes Secrets from OCI Vault. A single ClusterSecretStore named oci-vault is configured with Instance Principal auth — the OKE worker node identity is granted vault access via OCI Dynamic Group + Policy. No static OCI credentials anywhere.

Vault secrets currently in use:

  • cloudflared-tunnel-token — token for the homelab-tunnel Cloudflare Tunnel.
  • ocir-auth-token — pull credentials for OCIR. Copied as dockerconfigjson Secret into every application namespace (urlshortener, cv, infra, flux-system).
  • adb-admin-password — Autonomous Database ADMIN password, consumed by writer/reader pods as ADB_PASSWORD env var.

Each application namespace has an ExternalSecret resource that watches its Vault key and reconciles a Kubernetes Secret with refreshInterval: 1h. Vault is the single source of truth — rotate there, ESO propagates. Zero secrets are ever committed to Git.

Data layer

Autonomous JSON Database · SODA REST API over HTTPS

▼

Oracle Autonomous JSON Database (workload type: JSON, Always Free, 1 ECPU, 20 GB) hosted in the same region as the cluster. Accessed via the SODA REST API — plain HTTPS with Basic Auth — so the Go backend uses only the standard library's net/http. No Oracle client libraries, no mTLS wallet, no CGO; the resulting image stays distroless / static / non-root and ~12 MB compressed.

Schema: ADMIN.urls is a SODA collection with VARCHAR2 client-assigned keys (the short codes). Document shape:

{
  "long_url":   "https://...",
  "created_at": "ISO-8601"
}

This replaced an earlier OCI NoSQL backend after the NoSQL provisioned-capacity model started incurring small per-month charges in il-jerusalem-1 (Always Free NoSQL in this region uses different limits than what was provisioned). Migration was a same-day backend rewrite — storage interface unchanged, only the implementation file swapped.

Application architecture — URL Shortener

writer / reader / frontend split · 6 pods total

▼

The shortener is split into three Deployments in the urlshortener namespace, all running the same image with different MODE env vars (writer / reader) or a different image entirely (frontend):

  • writer — 2 replicas, handles POST /shorten and POST /createcustom. Generates short code, writes to ADB via SODA REST PUT.
  • reader — 2 replicas, handles GET /{6-char-code}. Reads from ADB, 301 redirects to the long URL.
  • frontend — 2 nginx pods, serves the static HTML form and assets.

writer/reader split is intentional: real URL shorteners have ~95% read traffic. Splitting them lets the reader scale independently (HPA candidate, eventually with a Redis read-through cache), keeps the writer image footprint minimal, and lets writers be drained for ADB migrations without affecting reads.

Pod budget across the cluster:

  • flux-system — 6 controllers
  • envoy-gateway-system — control plane + Envoy data plane (~3 pods)
  • external-secrets — controller + webhook + cert-controller (~3 pods)
  • cloudflare — cloudflared × 2
  • urlshortener — writer × 2, reader × 2, frontend × 2
  • cv — cv-frontend × 2
  • infra — infra-frontend × 2 (this page)
  • kube-system — metrics-server, CSI/CNI/kube-proxy DaemonSets

Repositories — multi-repo strategy

5 public repos · one per concern

▼

The platform is intentionally split across multiple public GitHub repos instead of a single monorepo. Each repo has its own CI/CD pipeline, its own container image, and is rolled out independently by Flux Image Automation. This mirrors how production microservices platforms are organized: service teams own a service repo, deployments are independent, the platform team owns the GitOps cluster repo.

  • AaronShemtov/urlshortener-backend — Go service running in writer or reader mode based on env var. SODA REST client, distroless image.
  • AaronShemtov/urlshortener-frontend — static HTML / CSS / JS form for shortening links, served by nginx-unprivileged.
  • AaronShemtov/cv-frontend — cv.1ms.my, the CV page with collapsible experience blocks and PDF downloads.
  • AaronShemtov/infra-frontend — infra.1ms.my, this very page.
  • AaronShemtov/personal-k8s — the GitOps source of truth. Contains every Flux Kustomization, HelmRelease, and Kubernetes manifest in the cluster. The only place where the platform's desired state is declared.

Cost of multi-repo: more places to track, more workflows to maintain. Benefit: real-world structure, independent release cadence per service, image-level versioning, no monolithic CI matrix.

Design decisions — and the alternatives rejected

Why these choices, not the obvious defaults

▼
  • Cloudflare Tunnel instead of OCI Load Balancer — preserves the single Always Free LB slot, eliminates inbound public IPs, includes DDoS protection and TLS termination at Cloudflare's edge for free.
  • Envoy Gateway, not nginx-ingress — Gateway API is the future of Kubernetes ingress. Envoy supports advanced traffic policies (rate-limit, JWT, ext-auth) natively, no plugin hacks required.
  • Flux instead of Argo CD — image automation is first-class (no separate Argo Image Updater needed), simpler operator model, easier multi-tenancy via Kustomization layering.
  • Multi-repo, not monorepo — independent CI, image-level versioning, role separation. Cost is more repos to remember; benefit is real-world structure that scales.
  • distroless/static:nonroot for Go services — ~5 MB final image, no shell, no package manager, no libc. An attacker who gets RCE can't exec into anything useful.
  • nginx-unprivileged for static sites — runs as UID 101, passes the restricted PodSecurityStandard without tweaks.
  • ARM64 (Ampere A1) everywhere — Always Free pool is Arm. Building Arm-native images avoids QEMU emulation at runtime and matches node arch.
  • ESO + Vault, not kubectl create secret or sealed-secrets — managed vault, native rotation, IAM audit log, no key material in Git history at any point.
  • Autonomous JSON DB over self-hosted Postgres in OKE — keeps PVC quota free for the future observability stack, gives zero-ops backups + monitoring, costs €0 in home region. Postgres-in-cluster would have eaten 50 GB of the 200 GB block volume budget.
  • Writer/reader split for a URL shortener — anticipates the 95/5 read/write ratio of real shortener traffic. Trivial to scale reads via HPA later, trivial to add a Redis read-through cache in front of the reader without touching the writer.
  • SODA REST over Oracle direct DB driver — Basic Auth over HTTPS works with stdlib net/http. No Oracle client binary, no wallet file mounted into the pod, no CGO breaking the distroless build.
  • No public OCI LoadBalancer, no public IPs anywhere — the cluster is reachable only through the outbound Cloudflare Tunnel. Smallest possible attack surface.
