Since client work is protected by NDA, this project serves as a showcase of the engineering practices I apply in professional environments. This is a platform that I designed, built, and operate.

multi-tenant kubernetes gitops image automation declarative ingress vault-sourced secrets zero secrets in git

Six public sites are hosted, all operated through GitOps from public GitHub, and two AI agent systems run next to them (agents, SRE agent). Every site and every platform component on top of the managed OKE cluster is declared in Git and applied by Flux, so releases reach the cluster as Git commits. The code is split across nine small public repositories, eight services with their own CI pipelines and one GitOps repository, to model the structure of a real microservices platform.

OCI

Cloud platform — Oracle Cloud Infrastructure

Region: il-jerusalem-1

The entire platform runs on Oracle Cloud Infrastructure (OCI) in the il-jerusalem-1 region. The services in active use:

  • Compute (Ampere A1) — two Arm-based VM.Standard.A1.Flex virtual machines with 2 OCPU each, one per OKE node pool.
  • Container Engine for Kubernetes (OKE) — managed Kubernetes control plane.
  • Block Volume — boot volumes for the worker nodes and one 50 GB volume for Prometheus, the only persistent volume in the cluster.
  • Container Registry (OCIR) — private repositories for the eight images the platform builds and runs.
  • Vault — master encryption keys and the secrets they protect. Source of truth for the credentials the workloads use; External Secrets Operator syncs them into Kubernetes Secrets.
  • Autonomous Database (JSON workload) — managed document store. The URL shortener uses it over SODA REST; the agents keep their memory in a separate schema over ORDS REST-Enabled SQL (see agents).
  • IAM (Dynamic Groups + Policies) — gives the worker nodes an instance-principal identity. External Secrets Operator uses it to read Vault, so reaching the vault needs no stored credential. The database password and the OCIR pull token are themselves Vault secrets.
ClusterSecretStore — Instance Principal auth into OCI Vault 
---

spec:

    oracle:
      vault: <vault-ocid>
      region: il-jerusalem-1
      principalType: InstancePrincipal
K8S

Kubernetes — OKE cluster

v1.34.10 · 2 worker nodes on v1.33.10 · VCN-Native CNI · OCI Block CSI

The cluster has two worker nodes, one in each of two node pools. Both are VM.Standard.A1.Flex Arm virtual machines with 2 OCPU and about 11 GB of memory, running Oracle Linux 9 with CRI-O:

  • main-pool — the observability stack: Prometheus, Alertmanager, Loki, Tempo, Grafana, kube-state-metrics and the Prometheus Operator are pinned to it with nodeSelector: name: main-pool.
  • apps-pool — only pwd-frontend is pinned to it.

Everything else, from the Flux controllers to the application pods, is scheduled across both nodes. Each node accepts at most 35 pods, and both are close to that limit.

The four static sites (aboutme, infra, secrets, myip), the URL shortener's writer, reader and frontend, and cloudflared run two replicas each with maxUnavailable: 0, so a rolling update never takes them below two ready pods. Their pod anti-affinity is preferred, not required: the scheduler spreads the replicas across the two nodes when it can, but both can land on one node, and pwd-frontend, pinned to a one-node pool, always has both replicas there.

The restricted Pod Security Standard is enforced on the seven application namespaces (aboutme, agents, ai-sre-agent, infra, myip, pwd, urlshortener). Every workload there runs as non-root, drops all Linux capabilities, uses the RuntimeDefault seccomp profile and mounts a read-only root filesystem. monitoring is labelled privileged, because node-exporter uses the host network, PID namespace and filesystem, and Loki keeps its data on a hostPath. The remaining namespaces, including flux-system, cloudflare, envoy-gateway-system, external-secrets and kube-system, carry no Pod Security label.

Live node CPU, memory and pod counts are on the Cluster Overview dashboard, the home page of grafana.1ms.my.

INGRESS

Networking and ingress

Envoy Gateway 1.2 · Gateway API v1.2.0 · ClusterIP only

The worker nodes have no public IP addresses, and every Service in the cluster is ClusterIP, so there is no load balancer to reach. All application traffic arrives through outbound Cloudflare Tunnel connections — see the Cloudflare section.

Inside the cluster, Envoy Gateway 1.2 (controller v1.2.8, Envoy proxy v1.32.4) implements the standard Kubernetes Gateway API; Flux applies the Gateway API v1.2.0 CRDs straight from the upstream repository. An EnvoyProxy custom resource explicitly pins the data-plane Service type to ClusterIP, overriding the default LoadBalancer behaviour. A single Gateway resource exposes one HTTP listener on port 80; allowedRoutes.namespaces.from: All permits HTTPRoute resources from any application namespace to attach without ReferenceGrants.

Hostname-based routing:

  • 1ms.my → urlshortener namespace (writer, reader, frontend Services selected by path)
  • aboutme.1ms.my → aboutme namespace (aboutme-frontend)
  • cv.1ms.my → no backend: an HTTPRoute in aboutme answers with a 301 redirect to aboutme.1ms.my
  • infra.1ms.my → infra namespace (infra-frontend, this page)
  • secrets.1ms.my → pwd namespace (pwd-frontend)
  • myip.1ms.my → myip namespace (myip-frontend)
  • grafana.1ms.my → monitoring namespace (grafana)

CLOUDFLARE

DNS, edge and tunnel — Cloudflare

Domain on Dynadot · DNS & proxy on Cloudflare · 2 tunnel connectors
  • Registrar — the 1ms.my domain is registered with Dynadot. The Dynadot domain has its nameservers delegated to Cloudflare, so Cloudflare hosts the authoritative DNS zone.
  • DNS — zone 1ms.my on Cloudflare. Each hostname the platform serves (apex, aboutme, cv, infra, secrets, myip, grafana) is a proxied CNAME pointing at the homelab tunnel. Cloudflare creates these records automatically when public hostnames are added to the tunnel.
  • Proxy (orange-cloud) — all traffic terminates TLS at Cloudflare's edge. This provides automatic TLS certificates, DDoS protection, edge caching of static assets, and HTTP analytics.
  • Cloudflare Tunnel — cloudflared runs as a 2-replica Deployment inside the cluster and opens outbound, encrypted QUIC connections to Cloudflare's edge. Each replica is one tunnel connector holding four connections, so the tunnel has 2 connectors and 8 connections, spread across Tel Aviv and Marseille edge POPs.
  • Tunnel hostnames route each domain to the in-cluster Envoy data-plane Service over HTTP. No workload accepts connections from the public internet; every request comes in through the tunnel.

FLUX

GitOps — Flux

Flux v2.6.4 · 6 controllers · Image Automation closes the loop

The cluster's desired state is declared in the AaronShemtov/personal-k8s repository. Flux reconciles the cluster against this repository every minute. Apart from the add-ons OKE manages itself in kube-system, every component the platform runs on — ingress, tunnel, secrets, monitoring and all seven application namespaces — is declared there and applied by Flux.

Six Flux controllers run in the flux-system namespace:

  • source-controller — pulls Git, OCI and Helm sources.
  • kustomize-controller — applies Kustomize overlays.
  • helm-controller — reconciles HelmReleases.
  • notification-controller — sends reconciliation errors and image updates to Telegram. No webhook receivers are configured; Flux polls Git.
  • image-reflector-controller — scans container registries for new tags.
  • image-automation-controller — commits image tag updates back to Git.

Three Kustomizations apply this repository:

  • flux-system — the bootstrap Kustomization, with path: ./ and a 1-minute interval. It applies the Flux components and, because it points at the repository root, every object under the two directories below as well.
  • infrastructure — applies everything under ./infrastructure/ (Gateway API CRDs, Envoy Gateway, External Secrets Operator, cloudflared, image automation, metrics-server, the monitoring stack with its dashboards, and Flux notifications to Telegram).
  • applications — applies everything under ./applications/ (urlshortener, aboutme, infra, pwd, myip, agents, ai-sre-agent). Depends on infrastructure being reconciled first; flux-system applies the same objects without that ordering.

The Git connection uses SSH with a write-enabled deploy key. The same key Flux uses to pull manifests is reused to push image tag updates produced by the Image Automation pipeline.

CI/CD

CI/CD pipeline — closed-loop GitOps

GitHub Actions → OCIR → Flux Image Automation → cluster

A push to any service repository propagates to running pods automatically. The diagram below shows the full loop:

Why GitHub Actions: it integrates directly with the source repository, provides build caches per repo, and runs at no additional cost on this scale. The OCI Ampere A1 compute pool is fully allocated to the OKE worker nodes, so an in-tenancy CI runner is not an option here.

Builds target linux/arm64 only, matching the Ampere A1 worker node architecture. The build itself runs natively on the GitHub-hosted amd64 runner; only the binary is cross-compiled via docker buildx. This avoids QEMU emulation entirely.

The four private OCIR repositories holding the images:

SECRETS

Secrets management

External Secrets Operator · OCI Vault · Instance Principal

External Secrets Operator (ESO) reconciles Kubernetes Secret resources from OCI Vault on a schedule. A single ClusterSecretStore named oci-vault is configured with Instance Principal authentication — the OKE worker node identity is granted Vault read access via an OCI Dynamic Group and Policy. No static cloud credentials are stored anywhere in the cluster or in Git.

Vault secrets currently in use:

  • cloudflared-tunnel-token — the token authorising the Cloudflare Tunnel.
  • ocir-auth-token — pull credentials for OCIR, materialised as a dockerconfigjson Secret in every application namespace.
  • adb-admin-password — Autonomous Database password, consumed by the writer and reader pods as the ADB_PASSWORD environment variable.

Every application namespace contains an ExternalSecret resource referencing the relevant Vault key. Rotation is performed in Vault and propagates within refreshInterval: 1h. No secret material is committed to Git at any point.

DATABASE

Data layer — Autonomous JSON Database

Managed document store · SODA REST API over HTTPS

The URL shortener persists its data in an Oracle Autonomous Database provisioned with the JSON workload type, in the same region as the cluster. The backend communicates with the database exclusively through the SODA REST API — standard HTTPS with HTTP Basic Authentication. The Go service therefore uses only the standard library's net/http; no Oracle client libraries, no mTLS wallet, no CGO. The resulting container image remains distroless, static, and non-root.

The schema is a single SODA collection named urls, with VARCHAR2 client-assigned keys (the short codes). Document shape:

{
  "long_url":   "https://...",
  "created_at": "ISO-8601 timestamp"
}
Live API — writer endpoint and the SODA REST call it makes internally 
$ curl -X POST https://1ms.my/shorten \
    -H "Content-Type: application/json" \
    -d '{"url":"https://docs.kubernetes.io/some/long/path"}'

$ curl -I https://1ms.my/abc123
HTTP/2 301
location: https://docs.kubernetes.io/some/long/path
SHORTENER

Application architecture — URL Shortener

Writer / reader / frontend split · independent scaling

The URL shortener is intentionally split into three independent Deployments in the urlshortener namespace. The split is a deliberate design decision aligned with the read/write asymmetry of a real shortener service.

  • writer (2 replicas) — handles POST /shorten and POST /createcustom. Generates the short code, writes the document to the Autonomous Database via SODA REST PUT, and returns the short URL to the caller. Started in MODE=writer via environment variable; the writer image registers only POST handlers.
  • reader (2 replicas) — handles GET /{6-char-code}. Reads the document from the database and returns a 301 redirect to the long URL. Started in MODE=reader.
  • frontend (2 nginx replicas) — serves the static single-page application that submits requests to the writer endpoint.

Why split writer from reader? A real URL shortener serves orders of magnitude more reads than writes — a single short link can be shared on social media and receive thousands of redirects per second while the write-side load remains effectively unchanged. By running the read path as a separate Deployment, the reader can scale horizontally (Horizontal Pod Autoscaler on CPU or request-rate) without provisioning additional writer capacity. The writer retains its small, predictable footprint. The two paths can also be deployed, drained, and rolled back independently — useful when migrating the storage backend or rolling out cache changes that affect only the read side.

Why the multi-Deployment, multi-namespace, multi-repository layout overall? The platform is structured to model a microservices architecture: each user-facing capability is its own Deployment (often its own namespace and source repository), with its own image, its own CI/CD pipeline, its own resource budget, and its own scaling profile. This mirrors how real production platforms are organised.

AGENTS

Agentic AI platform — lead, coder and reviewer agents

Telegram → lead agent → coder · reviewer · MCP servers for GitHub, cluster and Cloudflare

LLM agents that do engineering work on this platform, driven from Telegram. They run in the agents namespace as six single-replica Deployments from one repository, AaronShemtov/ai-agents-platform: five run the same image with different commands, and the GitHub MCP server is GitHub's own image. An agent is configuration rather than code: a profile in agents/*.yaml sets its system prompt, the tools it may call, its model and its step and token limits. CI runs ruff, imports every entrypoint and runs the test suite, then builds the image on a native arm64 runner.

  • agent-lead — the only agent with a Telegram bot, and the one a person talks to. It reads the cluster, works in GitHub and Cloudflare, and hands work to the other two. The bot answers allow-listed Telegram users only; an empty list refuses everyone.
  • agent-coder — writes application code, Dockerfiles, workflows and manifests. It has no bot, because Telegram never delivers one bot's messages to another; the lead reaches it over the cluster network as one more MCP tool, coder__ask, checked and logged like any other call.
  • agent-reviewer — reads a change and answers APPROVE or CHANGES REQUESTED; the lead's instructions send every change to it before the work is reported as done. It runs on a different model from the coder, so the review does not inherit the author's blind spots, and it cannot write: its profile allows only read tools and its GitHub write mode is read-only.
  • mcp-github, mcp-cluster, mcp-cloudflare — the tools, served over MCP's streamable HTTP transport inside the cluster.

One credential boundary per pod

The limits that matter sit outside the model's reach, in Kubernetes objects and server flags kept in Git:

  • mcp-cluster — the only identity in the namespace with Kubernetes permissions: a ClusterRole with get, list and watch on pods, logs, events, workloads, Services, ConfigMaps and routes. No Secrets, no exec, no write verb. Its readiness probe calls the API server, so broken RBAC shows up as NotReady.
  • mcp-cloudflare — the only holder of the Cloudflare API token. It exposes 14 tools written for this platform (DNS records, WAF rules, tunnel hostnames, cache purge) and nothing else, and its readiness probe checks the token against Cloudflare.
  • mcp-github — GitHub's own MCP server, self-hosted so that its toolsets are fixed by flags in Git and enforced server-side. It holds no credential: each agent sends its GitHub token with every request.
  • The agents — hold the model API key and the GitHub token, and have no Kubernetes permissions at all.

Local policy and human approval

Every tool call the model proposes passes a policy check inside the agent before it is sent, and the check reads the arguments, not only the tool name. Each profile also limits which tools the model sees at all; github__delete_* is denied to all three agents.

  • Reads pass. A tool counts as a read only by its verb (get_, list_, search_ and similar). Anything else is treated as a write, and a tool from an unknown server needs approval.
  • The GitOps repository takes pull requests only. A write to the default branch of personal-k8s is refused in every write mode. Creating a branch or a pull request is allowed, and merging one asks for approval, because Flux applies the result to the live cluster.
  • Cloudflare changes and delegation to the coder ask first. A bad commit can be reverted; a deleted DNS record takes a site offline until someone notices. Cluster writes are refused outright, and the ClusterRole could not perform them anyway.
  • Approval happens in Telegram. The lead posts the tool and its complete arguments, with Approve and Reject buttons on the last message, and waits. No answer within ten minutes counts as a rejection, and the allow-list is checked again on the button press. The coder and the reviewer have nobody to ask, so a call that needs approval is refused there and reported back to the lead.

Models and memory

  • Azure AI Foundry — the lead defaults to gpt-5.6-luna and can be switched per chat with /model; the coder runs gpt-5.3-codex and the reviewer gpt-5.1-codex-max. The client sends each deployment to the Responses or the Chat Completions API as configured, and web search runs as an Azure-hosted tool on the Responses API.
  • Optional self-hosted model — Qwen3.6-35B-A3B on Ollama, on a CPU-only machine outside the cluster, reached through its own Cloudflare Tunnel; requests without a shared secret are refused at the edge. Chosen with /model, it gets a short prompt and no tools.
  • Durable memory — the lead's chat history and the facts it keeps about the user live in the same Autonomous Database as the URL shortener, but in a schema of their own with no grants on the shortener's data. The agent reaches it through ORDS REST-Enabled SQL: plain HTTPS, no Oracle client and no wallet. History is replayed after a restart; /memories lists the stored facts and /forget removes one.

Telemetry and audit

The lead and the coder expose Prometheus metrics under the OpenTelemetry GenAI names (gen_ai_client_token_usage, gen_ai_client_operation_duration_seconds, gen_ai_execute_tool_duration_seconds and the agent-invocation histograms), plus agent_* series for policy decisions, approvals and how long a person took to answer. They feed the AI Agents dashboard, next to Azure Monitor metrics for the model resource. Every tool call is also one JSON audit line in the pod log, collected into Loki, with the arguments hashed rather than written out.

SRE

AI SRE agent — incident investigation with approval-gated fixes

Telegram · LangGraph · Gemini 2.5 Flash-Lite · reads broadly, patches two things

A single-purpose agent in its own namespace, ai-sre-agent, from AaronShemtov/ai-sre-agent. Asked in Telegram why a workload is unhealthy, for example why does urlshortener-reader keep restarting, it reads the live cluster and replies with a root-cause analysis: probable cause, timeline, blast radius, the evidence behind it and a suggested fix. When one of two safe fixes applies, it offers to run it.

Investigation flow

A LangGraph graph with fixed steps decides which cluster calls happen. The model only reads what was collected and proposes; it never calls the Kubernetes API itself.

  1. Gather, with no model involved. The namespace is matched from the question against the real namespace list. The agent then reads pods and events and, for up to five unhealthy pods, their details and last 80 log lines, including the previous container's logs after a crash, plus the Deployment, Service and Endpoints behind them.
  2. Analyse, in one model call. Gemini 2.5 Flash-Lite turns the signals into the RCA as strict JSON, is told to cite only what is in the data, and may propose at most one action. A proposal naming anything other than the two registered fixes is dropped. One call per investigation keeps the agent inside the free tier's daily request quota.
  3. Approve. A proposed action arrives with Approve and Reject buttons, and nothing changes until an allow-listed user presses Approve. The user is checked again on the button press, since anyone who can see the message can press it. An empty allow-list refuses everyone.
  4. Execute and verify. A second graph runs the approved action and reads the result back: ready replicas after a restart, ready endpoints after a selector fix.

What it can and cannot change

  • Two actions — a rolling restart of a Deployment, and a new selector for a Service whose selector no longer matches its pods' labels. Its ClusterRole grants patch on Deployments and Services and no other write.
  • Read access — get, list and watch on pods, logs, events, workloads, Services, Endpoints, ConfigMaps, nodes, namespaces, Ingresses and HTTPRoutes. No Secrets, no exec or attach, no create or delete, no wildcards.
  • Git still wins — on objects Flux manages, the lasting fix is a commit: Flux reconciles the applications from Git every 10 minutes and puts back the fields it manages. The lead agent above works the other way round and changes the cluster only through a pull request.
  • Limits — logs come from the Kubernetes API, not yet from Loki or Prometheus. A pending approval lives in memory and is lost if the pod restarts. It runs as one replica with the Recreate strategy, because a Telegram bot token allows only one poller.

REPOS

Repositories — multi-repository strategy

Six public repositories · one per concern · modeled on microservices

The platform is intentionally split across six public repositories rather than a single monorepo. Each repository owns one concern: it has its own CI/CD workflow, its own container image, and is rolled out independently by Flux Image Automation. This structure deliberately models a real microservices platform, where each service team owns a repository and the platform team owns the GitOps cluster repository.

  • AaronShemtov/urlshortener-backend — Go service running in writer or reader mode, selected by environment variable. SODA REST client, distroless image.
  • AaronShemtov/urlshortener-frontend — static HTML, CSS and JavaScript form, served by nginx-unprivileged.
  • AaronShemtov/cv-frontend — the CV site at aboutme.1ms.my.
  • AaronShemtov/infra-frontend — this page.
  • AaronShemtov/pwd-frontend — the password generator at secrets.1ms.my; client-side cryptographic generation, no backend.
  • AaronShemtov/personal-k8s — the GitOps source of truth. Contains every Flux Kustomization, HelmRelease and Kubernetes manifest reconciled against the cluster.
03 ·

Design decisions

Why these choices, and the alternatives rejected.

Platform & networking

  • Cloudflare Tunnel instead of an OCI Load Balancereliminates inbound public IPs entirely. TLS termination, DDoS protection and edge caching are handled by Cloudflare. The cluster has no exposed ports.
  • Envoy Gateway over nginx-ingressadopts the standardised Kubernetes Gateway API, which supports advanced traffic policies (rate limiting, JWT validation, external authorisation) natively.
  • Flux over Argo CDImage Automation is a first-class capability of Flux, removing the need for a separate Argo Image Updater. The operator model is simple and the Kustomization layering supports multi-tenancy without additional tooling.
  • Multi-repository, not monorepoindependent CI/CD, image-level versioning, clear ownership boundaries. Models a real microservices platform.
  • ARM64 (Ampere A1) workloads end-to-endevery image built here targets linux/arm64 to match the worker nodes, so nothing runs under emulation in the cluster. The Go backend cross-compiles on the amd64 runner, and the agents platform builds on a native arm64 runner.
  • No public ingress, no bootstrap credentialevery external connection enters through the outbound Cloudflare Tunnel, and no Service is of type LoadBalancer or NodePort. External Secrets reads OCI Vault as the node itself (Instance Principal), so no API key is needed to fetch the others; application credentials are synced from Vault, never committed to Git.
  • Storage within the Always Free budgetAlways Free includes 200 GB of block storage in total, boot volumes included, and oci-bv never provisions less than 50 GB per volume. So the cluster has exactly one volume: 50 GB for Prometheus, with 60-day retention. Loki keeps 30 days on the node's own disk, which survives pod restarts but is lost if the node is replaced. Grafana, Alertmanager and Tempo keep no persistent volume; their configuration comes back from Git and Vault on every start.

Images, secrets & data

  • distroless/static:nonroot base for Go servicesfinal image is small, has no shell, no package manager, no libc, and runs as a non-root user by default. Reduces attack surface and image size simultaneously.
  • nginx-unprivileged for static sitesruns as UID 101, passes the restricted Pod Security Standard out of the box.
  • External Secrets Operator with OCI Vaultmanaged vault with native rotation and IAM audit; no secret material is ever committed to Git.
  • Managed Autonomous Database over in-cluster Postgreskeeps database storage off the cluster's Always Free block-volume budget, which goes to Prometheus, and leaves patching and operation to Oracle. The agents' memory lives in the same instance, in a schema of its own.
  • Writer / reader split for the URL shorteneraligns with the read-heavy traffic profile and enables independent scaling of the read path.
  • Turnstile or an API key on the shortener's write path, failing closedPOST /shorten and /createcustom need a Cloudflare Turnstile token, which the widget on the page obtains for a browser and the writer verifies with Cloudflare, or an X-API-Key header for scripts. No proof is a 403 and an unreachable verifier a 503, never a pass, and the writer refuses to start unless at least one of the two secrets is set.
  • SODA REST instead of a native Oracle DB driverkeeps the Go service's container image distroless and CGO-free, with no client library or wallet mount.
