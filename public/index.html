OCI

Cloud platform — Oracle Cloud Infrastructure

Region: il-jerusalem-1

The entire platform runs on Oracle Cloud Infrastructure (OCI) in the il-jerusalem-1 region. The services in active use:

  • Compute (Ampere A1) — Arm-based virtual machines allocated as the OKE worker pool.
  • Container Engine for Kubernetes (OKE) — managed Kubernetes control plane.
  • Block Volume — boot volumes for worker nodes; later, persistent volumes for the observability stack.
  • Container Registry (OCIR) — private repositories for every application image.
  • Vault — master encryption keys and tenancy-managed secrets. Source of truth for all runtime credentials.
  • Autonomous Database (JSON workload) — managed document store accessed over SODA REST.
  • IAM (Dynamic Groups + Policies) — grants the OKE worker node identity scoped access to Vault secrets and the database, eliminating static cloud credentials.

K8S

Kubernetes — OKE cluster

v1.32.1 · 3 worker nodes · VCN-Native CNI · OCI Block CSI

The cluster has three worker nodes, intentionally heterogeneous in capacity:

  • 10.0.1.37 — 1 OCPU / 6 GB RAM — application workloads.
  • 10.0.1.66 — 1 OCPU / 6 GB RAM — application workloads, paired with .37 through pod anti-affinity for HA during rolling updates.
  • 10.0.1.135 — 2 OCPU / 12 GB RAM — reserved for the observability stack (Prometheus, Grafana, Loki), which will be deployed in a future iteration.

The asymmetric split provides one larger node sized for memory-heavy observability workloads while keeping two smaller application nodes whose loss is absorbed by anti-affinity-spread replicas.

The restricted Pod Security Standard is enforced per namespace. All workloads run as non-root, drop all Linux capabilities, use the RuntimeDefault seccomp profile, and mount a read-only root filesystem where the application permits.

INGRESS

Networking and ingress

Envoy Gateway · Kubernetes Gateway API · ClusterIP only

The cluster has no public IP address and no inbound firewall openings. There is no public load balancer attached to any Service. All ingress is delivered through outbound Cloudflare Tunnel connections — see the Cloudflare section.

Inside the cluster, Envoy Gateway 1.x implements the standard Kubernetes Gateway API. An EnvoyProxy custom resource explicitly pins the data-plane Service type to ClusterIP, overriding the default LoadBalancer behaviour. A single Gateway resource exposes one HTTP listener on port 80; allowedRoutes.namespaces.from: All permits HTTPRoute resources from any application namespace to attach without ReferenceGrants.

Hostname-based routing:

  • 1ms.my → urlshortener namespace (writer, reader, frontend Services selected by path)
  • cv.1ms.my → cv namespace (cv-frontend)
  • infra.1ms.my → infra namespace (this page)

CLOUDFLARE

DNS, edge and tunnel — Cloudflare

Domain on Dynadot · DNS & proxy on Cloudflare · 4 tunnel connectors
  • Registrar — the 1ms.my domain is registered with Dynadot. The Dynadot domain has its nameservers delegated to Cloudflare, so Cloudflare hosts the authoritative DNS zone.
  • DNS — zone 1ms.my on Cloudflare. Each subdomain (apex, cv, infra) is a CNAME pointing at the homelab tunnel. Cloudflare creates these records automatically when public hostnames are added to the tunnel.
  • Proxy (orange-cloud) — all traffic terminates TLS at Cloudflare's edge. This provides automatic TLS certificates, DDoS protection, edge caching of static assets, and HTTP analytics.
  • Cloudflare Tunnel — cloudflared runs as a 2-replica Deployment inside the cluster and establishes outbound TLS connections to Cloudflare's edge. The tunnel currently reports HEALTHY with 4 connectors across Tel Aviv and Marseille edge POPs.
  • Tunnel hostnames route each domain to the in-cluster Envoy data-plane Service over HTTP. The cluster never accepts unsolicited inbound traffic from the public internet.

FLUX

GitOps — Flux

Flux v2.6.4 · 6 controllers · Image Automation closes the loop

The cluster's desired state is declared entirely in the AaronShemtov/personal-k8s repository. Flux reconciles the cluster against this repository every minute. The repository is the single source of truth — there is no production change that is not first a Git commit.

Six Flux controllers run in the flux-system namespace:

  • source-controller — pulls Git, OCI and Helm sources.
  • kustomize-controller — applies Kustomize overlays.
  • helm-controller — reconciles HelmReleases.
  • notification-controller — emits alerts and receives webhooks.
  • image-reflector-controller — scans container registries for new tags.
  • image-automation-controller — commits image tag updates back to Git.

Two root Kustomizations layer the cluster:

  • infrastructure — applies everything under ./infrastructure/ (Gateway API CRDs, Envoy Gateway, External Secrets Operator, cloudflared, image-automation, metrics-server).
  • applications — applies everything under ./applications/ (urlshortener, cv, infra). Depends on infrastructure being reconciled first.

The Git connection uses SSH with a write-enabled deploy key. The same key Flux uses to pull manifests is reused to push image tag updates produced by the Image Automation pipeline.

CI/CD

CI/CD pipeline — closed-loop GitOps

GitHub Actions → OCIR → Flux Image Automation → cluster

A push to any service repository propagates to running pods automatically. The diagram below shows the full loop:

Why GitHub Actions: it integrates directly with the source repository, provides build caches per repo, and runs at no additional cost on this scale. The OCI Ampere A1 compute pool is fully allocated to the OKE worker nodes, so an in-tenancy CI runner is not an option here.

Builds target linux/arm64 only, matching the Ampere A1 worker node architecture. The build itself runs natively on the GitHub-hosted amd64 runner; only the binary is cross-compiled via docker buildx. This avoids QEMU emulation entirely.

The four private OCIR repositories holding the images:

GitHub Actions workflow — urlshortener-backend/.github/workflows/build-and-push.yml 
name: build-and-push

on:
  push:
    branches: [main]
  workflow_dispatch:

concurrency:
  group: build-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build-push:
    runs-on: ubuntu-latest

    permissions:
      contents: read

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to OCIR
        uses: docker/login-action@v3
        with:
          registry: il-jerusalem-1.ocir.io
          username: axiwhc5fgu9i/shemtov.aaron@gmail.com
          password: ${{ secrets.OCIR_AUTH_TOKEN }}

      - name: Resolve image tags
        id: tag
        run: |
          echo "sha=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"
          echo "ver=0.0.${{ github.run_number }}" >> "$GITHUB_OUTPUT"

      - name: Build and push
        uses: docker/build-push-action@v6

          context: .
          platforms: linux/arm64
          push: true

            il-jerusalem-1.ocir.io/axiwhc5fgu9i/urlshortener-backend:${{ steps.tag.outputs.sha }}

          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Summary
        run: |
          echo "### Image pushed :rocket:" >> $GITHUB_STEP_SUMMARY
          echo "" >> $GITHUB_STEP_SUMMARY
          echo "- Version tag (used by Flux): \`${{ steps.tag.outputs.ver }}\`" >> $GITHUB_STEP_SUMMARY

SECRETS

Secrets management

External Secrets Operator · OCI Vault · Instance Principal

External Secrets Operator (ESO) reconciles Kubernetes Secret resources from OCI Vault on a schedule. A single ClusterSecretStore named oci-vault is configured with Instance Principal authentication — the OKE worker node identity is granted Vault read access via an OCI Dynamic Group and Policy. No static cloud credentials are stored anywhere in the cluster or in Git.

Vault secrets currently in use:

  • cloudflared-tunnel-token — the token authorising the Cloudflare Tunnel.
  • ocir-auth-token — pull credentials for OCIR, materialised as a dockerconfigjson Secret in every application namespace.
  • adb-admin-password — Autonomous Database password, consumed by the writer and reader pods as the ADB_PASSWORD environment variable.

Every application namespace contains an ExternalSecret resource referencing the relevant Vault key. Rotation is performed in Vault and propagates within refreshInterval: 1h. No secret material is committed to Git at any point.

DATABASE

Data layer — Autonomous JSON Database

Managed document store · SODA REST API over HTTPS

The URL shortener persists its data in an Oracle Autonomous Database provisioned with the JSON workload type, in the same region as the cluster. The backend communicates with the database exclusively through the SODA REST API — standard HTTPS with HTTP Basic Authentication. The Go service therefore uses only the standard library's net/http; no Oracle client libraries, no mTLS wallet, no CGO. The resulting container image remains distroless, static, and non-root.

The schema is a single SODA collection named urls, with VARCHAR2 client-assigned keys (the short codes). Document shape:

{
  "long_url":   "https://...",
  "created_at": "ISO-8601 timestamp"
}
Live API — writer endpoint and the SODA REST call it makes internally 
$ curl -X POST https://1ms.my/shorten \
    -H "Content-Type: application/json" \
    -d '{"url":"https://docs.kubernetes.io/some/long/path"}'

$ curl -I https://1ms.my/abc123
HTTP/2 301
location: https://docs.kubernetes.io/some/long/path
SHORTENER

Application architecture — URL Shortener

Writer / reader / frontend split · independent scaling

The URL shortener is intentionally split into three independent Deployments in the urlshortener namespace. The split is a deliberate design decision aligned with the read/write asymmetry of a real shortener service.

  • writer (2 replicas) — handles POST /shorten and POST /createcustom. Generates the short code, writes the document to the Autonomous Database via SODA REST PUT, and returns the short URL to the caller. Started in MODE=writer via environment variable; the writer image registers only POST handlers.
  • reader (2 replicas) — handles GET /{6-char-code}. Reads the document from the database and returns a 301 redirect to the long URL. Started in MODE=reader.
  • frontend (2 nginx replicas) — serves the static single-page application that submits requests to the writer endpoint.

Why split writer from reader? A real URL shortener serves orders of magnitude more reads than writes — a single short link can be shared on social media and receive thousands of redirects per second while the write-side load remains effectively unchanged. By running the read path as a separate Deployment, the reader can scale horizontally (Horizontal Pod Autoscaler on CPU or request-rate) without provisioning additional writer capacity. The writer retains its small, predictable footprint. The two paths can also be deployed, drained, and rolled back independently — useful when migrating the storage backend or rolling out cache changes that affect only the read side.

Why the multi-Deployment, multi-namespace, multi-repository layout overall? The platform is structured to model a microservices architecture: each user-facing capability is its own Deployment (often its own namespace and source repository), with its own image, its own CI/CD pipeline, its own resource budget, and its own scaling profile. This mirrors how real production platforms are organised.

OBS

Observability — Prometheus, Loki, Grafana

live · public dashboards at grafana.1ms.my

The observability stack is live and operating on the larger 2 OCPU / 12 GB observability node (10.0.1.135). Anonymous read-only access is enabled — anyone visiting grafana.1ms.my lands directly on the home dashboard without a login. Admin sign-in uses a credential pair reconciled from OCI Vault via External Secrets Operator.

Components, all pinned to specific versions:

  • Alertmanager 0.27 — alert routing. Currently with a no-op receiver; Telegram bot integration is the next iteration.
  • Loki 3.2 in SingleBinary mode — log aggregation, filesystem storage on PVC.
  • Grafana Alloy 1.5 as a DaemonSet on every node — tails container logs, enriches with Kubernetes metadata, ships to Loki.
  • Grafana 11.3.9 — visualisation, with two data sources wired (Prometheus + Loki) and ~30 dashboards pre-provisioned (4 hand-built + the full kubernetes-mixin set from kube-prometheus-stack).
  • node-exporter DaemonSet for node-level metrics on all three workers.
  • kube-state-metrics for Pod/Deployment/etc state.

The home dashboard — node count, total running pods, restart counters, and resource graphs — is the entry point for anyone evaluating the platform:

Pod placement and isolation

All stateful observability pods (Prometheus, Alertmanager, Loki, Grafana, kube-state-metrics, the Prometheus Operator itself) are pinned to the observability node via a nodeSelector: workload=observability on the node and matching selectors in every HelmRelease. DaemonSets (node-exporter, Alloy) run on every node by design — that's where the data is.

Each PVC starts intentionally small — 5 GiB Prometheus, 5 GiB Loki, 2 GiB Grafana, 1 GiB Alertmanager — about 13 GiB total. With Always Free providing 200 GiB of Block Volume and the underlying volumes supporting online expansion, the plan is to observe actual growth for a week, then resize via GitOps. Bumping a PVC happens by editing the HelmRelease values, committing, and letting Flux apply — no kubectl edit against live state.

Logs — Loki + Alloy

Alloy runs as a DaemonSet on every node, tails container logs from /var/log/pods/, attaches Kubernetes labels (namespace, pod, container, node) as Loki stream labels, and ships to the Loki SingleBinary on the observability node. Retention is set to 7 days, enforced by Loki's compactor.

Standard kubernetes dashboards

The kube-prometheus-stack chart provisions the full kubernetes-mixin dashboard set as ConfigMaps. The Grafana sidecar discovers them by label and imports them on startup — without any further configuration the cluster gets the canonical dashboards every Kubernetes engineer expects: API server, kubelet, Compute Resources per cluster/namespace/node/pod/workload, networking, persistent volumes, and more.

Public access architecture

Grafana is exposed publicly through the same path as the other sites — an HTTPRoute on the homelab Gateway, traffic arriving via the existing Cloudflare Tunnel. The Grafana config sets auth.anonymous with org_role: Viewer, which lets anyone see the dashboards. The login form is still available — admin signs in with credentials reconciled from OCI Vault via two ExternalSecrets:

REPOS

Repositories — multi-repository strategy

Six public repositories · one per concern · modeled on microservices

The platform is intentionally split across six public repositories rather than a single monorepo. Each repository owns one concern: it has its own CI/CD workflow, its own container image, and is rolled out independently by Flux Image Automation. This structure deliberately models a real microservices platform, where each service team owns a repository and the platform team owns the GitOps cluster repository.

  • AaronShemtov/urlshortener-backend — Go service running in writer or reader mode, selected by environment variable. SODA REST client, distroless image.
  • AaronShemtov/urlshortener-frontend — static HTML, CSS and JavaScript form, served by nginx-unprivileged.
  • AaronShemtov/cv-frontend — the CV site at cv.1ms.my.
  • AaronShemtov/infra-frontend — this page.
  • AaronShemtov/pwd-frontend — the password generator at pwd.1ms.my; client-side cryptographic generation, no backend.
  • AaronShemtov/personal-k8s — the GitOps source of truth. Contains every Flux Kustomization, HelmRelease and Kubernetes manifest reconciled against the cluster.
03 ·

Design decisions

Why these choices, and the alternatives rejected.

Platform & networking

  • Cloudflare Tunnel instead of an OCI Load Balancereliminates inbound public IPs entirely. TLS termination, DDoS protection and edge caching are handled by Cloudflare. The cluster has no exposed ports.
  • Envoy Gateway over nginx-ingressadopts the standardised Kubernetes Gateway API, which supports advanced traffic policies (rate limiting, JWT validation, external authorisation) natively.
  • Flux over Argo CDImage Automation is a first-class capability of Flux, removing the need for a separate Argo Image Updater. The operator model is simple and the Kustomization layering supports multi-tenancy without additional tooling.
  • Multi-repository, not monorepoindependent CI/CD, image-level versioning, clear ownership boundaries. Models a real microservices platform.
  • ARM64 (Ampere A1) workloads end-to-endmatches the worker node architecture, removing QEMU emulation at both build time and runtime.
  • No public ingress, no static credentialsevery external connection enters through the outbound Cloudflare Tunnel; every cloud credential is short-lived and scoped via Instance Principal.

Images, secrets & data

  • distroless/static:nonroot base for Go servicesfinal image is small, has no shell, no package manager, no libc, and runs as a non-root user by default. Reduces attack surface and image size simultaneously.
  • nginx-unprivileged for static sitesruns as UID 101, passes the restricted Pod Security Standard out of the box.
  • External Secrets Operator with OCI Vaultmanaged vault with native rotation and IAM audit; no secret material is ever committed to Git.
  • Managed Autonomous Database over in-cluster Postgresfrees the cluster's block-volume budget for the upcoming observability stack and removes operational burden (backups, upgrades, monitoring).
  • Writer / reader split for the URL shorteneraligns with the read-heavy traffic profile and enables independent scaling of the read path.
  • SODA REST instead of a native Oracle DB driverkeeps the Go service's container image distroless and CGO-free, with no client library or wallet mount.

Decision log — incidents, fixes, lessons

Real problems encountered while building and operating this platform — what broke, how it was tracked down, what fixed it, and what was learned.

INC

Flux self-update wiped every controller in the cluster

flux bootstrap · server-side apply · annotation-size limit

Problem. Regenerating flux-system/gotk-components.yaml with --components-extra=image-reflector-controller,image-automation-controller, the kustomize-controller deleted the four existing Flux Deployments before the new ones came up. The reconcile then failed because the kustomize-controller itself was the resource being replaced. Cluster ended up with zero Flux controllers running — and with no Flux, nothing reconciled.

Investigation. kubectl get pods -n flux-system showed an empty namespace; describe on the Kustomization showed a timeout. The manifest itself was over Kubernetes' annotation-size limit when applied through the standard client-side merge path, so a normal kubectl apply -f rejected it.

Fix. kubectl apply -f gotk-components.yaml --server-side --force-conflicts — server-side apply bypasses the annotation-size limit. The controllers came back, picked up the GitRepository, and reconciliation resumed.

Lesson. Never bootstrap or upgrade Flux through a Kustomization that depends on Flux itself. The components install is an out-of-band step; the rest is GitOps. Also: --server-side is the correct flag for any manifest larger than a handful of KB.

INC

OCI NoSQL started charging — same-day migration to Autonomous JSON Database

cost surprise · storage interface swap · ~3 hours to production

Problem. The URL shortener's original storage was OCI NoSQL, configured for what looked like the Always Free tier. Two billing cycles later a small monthly charge appeared — the Always Free terms for NoSQL in il-jerusalem-1 had changed and the provisioned-capacity model no longer fit under them.

Investigation. The OCI Cost Analysis view broke the bill down to the NoSQL table specifically. Autonomous JSON Database (workload type JSON) was Always Free in the same region with 1 ECPU and 20 GB included — much more headroom and managed backups out of the box.

Fix. Drop-in replacement of the Storage interface implementation: a new SodaStore talking to ORDS via plain HTTPS Basic Auth, no Oracle client libraries needed. The interface itself did not change; only the file under internal/storage/ was swapped, plus the ExternalSecret in personal-k8s for the new database password. Total elapsed time from "billing alert" to "new backend deployed via Flux Image Automation": about three hours.

Lesson. An abstraction is worth keeping even on a one-service project. With a thin Storage interface, this was a file swap rather than a refactor. Pragmatic Go interfaces pay for themselves the first time the backend changes.

INC

SODA REST returned 503 for a dedicated database user

always free limitation · pragmatic compromise

Problem. Best practice says application services connect under a least-privilege schema, not as ADMIN. So I created a URLSHORTENER user, granted privileges, ran ORDS_ADMIN.ENABLE_SCHEMA, and tried to use /ords/urlshortener/soda/latest/urls. The response was a 503 ServiceUnavailable with an ECID and no further information.

Investigation. The schema appeared in DBA_ORDS_SCHEMAS as enabled. ADMIN-side endpoints (/ords/admin/soda/latest/) worked perfectly. On Always Free Autonomous Database, REST-enabling a non-ADMIN schema for SODA is restricted by the managed-instance configuration in ways that are not user-controllable. The OCI Console offers no toggle for it.

Fix. Use the ADMIN schema for the application connection. Document the trade-off explicitly: this is acceptable for a personal demonstration project but would not be acceptable for client work, where a self-managed Oracle deployment or a different DBaaS would give the granular IAM control that Always Free withholds.

Lesson. Managed services trade flexibility for operational simplicity. Knowing exactly where that trade-off bites — and being able to say so honestly when interviewed — matters more than pretending the limitation does not exist. The right move is to document the compromise, not hide it.

INC

Pods stuck — namespace rename forgot the ServiceAccount reference

kubectl get events · admission failure · the obvious place to look

Problem. The infra-frontend Deployment was copied from the cv-frontend manifest. The ReplicaSet was created but no pods came up. kubectl get pods -n infra returned an empty list.

Investigation. kubectl get events -n infra --sort-by='.lastTimestamp' told the whole story immediately: error looking up service account infra/cv: serviceaccount "cv" not found. The manifest copy had updated every reference from cv to infra except serviceAccountName: cv.

Fix. One-line edit, one git commit, one Flux reconcile. Pods came up in under a minute.

Lesson. When pods do not appear, the next command after kubectl get pods is always kubectl get events in that namespace. Kubernetes is loud about admission failures — the information is right there. Also: copy-paste between namespaces is a smell. The proper long-term fix is Kustomize overlays with a single base manifest.

INC

Flux Image Automation pushes failed silently after switching from PAT to SSH

runtime patch vs git source-of-truth · the GitOps lesson

Problem. The Flux GitRepository was originally configured with HTTPS and a personal access token. As the PAT expiration approached, I switched to SSH using a deploy key with write access. Pull worked immediately. Image Automation, however, kept producing "no new updates" even after pushing new OCIR tags it should have committed back.

Investigation. kubectl patch gitrepository updated the runtime URL to ssh://…, but kustomize-controller kept resetting it to the HTTPS URL stored in flux-system/gotk-sync.yaml. Image Automation was therefore attempting to push to an HTTPS URL with no credentials.

Fix. The runtime patch on a Flux-managed resource is always overwritten by the next reconcile. The source of truth is the YAML in the GitRepository itself. I updated gotk-sync.yaml to the SSH URL, committed, and reconciled. The image-automation-controller began pushing tag bumps within minutes.

Lesson. In GitOps there is only one source of truth and it lives in the repository. kubectl edit and kubectl patch on Flux-managed resources are diagnostic tools, not configuration tools. If a change has to stick, it goes through Git.

INC

Pinned Grafana to a non-existent image tag · ImagePullBackOff

helm chart version ≠ app version · double-prefix gotcha

Problem. While rolling out the observability stack I pinned the Grafana image explicitly to make the version predictable. After the next Flux reconcile the Grafana pod was stuck in ImagePullBackOff, and because the infrastructure Kustomization waits for all HelmReleases to be Ready, the whole reconcile loop blocked — including the applications Kustomization that depends on infrastructure.

Investigation. kubectl describe pod showed two distinct issues stacked on top of each other. First, the image path read docker.io/docker.io/grafana/grafana — a double prefix. The Grafana Helm chart prepends docker.io/ automatically when the repository value doesn't start with a registry, and I'd written docker.io/grafana/grafana in values, producing the duplication. Second, the tag I'd chosen — 11.3.0 — didn't actually exist on Docker Hub; the chart's default appVersion at the time was 11.2.1.

Fix. Two parts. The repository field should be just the path grafana/grafana — let the chart handle the registry prefix. The tag should be a tag that demonstrably exists. After verifying available tags at hub.docker.com/r/grafana/grafana/tags, I pinned to 11.3.9 — a real existing patch release of the 11.3 series. Once both were corrected and committed, the pod started cleanly and the dependent Kustomizations unblocked.

Lesson. Helm chart version and application appVersion are different release cadences. chart: grafana@8.5.2 ships with whatever appVersion the chart maintainer chose — at the time of writing that was 11.2.1. Pinning the chart version is enough for reproducibility; pinning the image tag too is double-pinning, justified when there's a concrete reason (in this case: getting a 11.3.x patch ahead of the chart's update cycle). Whenever an image tag is typed by hand, the registry tag list is the source of truth — guessing creates the exact failure I caused.
