OCI

Cloud platform — Oracle Cloud Infrastructure

Region: il-jerusalem-1

The entire platform runs on Oracle Cloud Infrastructure (OCI) in the il-jerusalem-1 region. The services in active use:

  • Compute (Ampere A1) — Arm-based virtual machines allocated as the OKE worker pool.
  • Container Engine for Kubernetes (OKE) — managed Kubernetes control plane.
  • Block Volume — boot volumes for worker nodes; later, persistent volumes for the observability stack.
  • Container Registry (OCIR) — private repositories for every application image.
  • Vault — master encryption keys and tenancy-managed secrets. Source of truth for all runtime credentials.
  • Autonomous Database (JSON workload) — managed document store accessed over SODA REST.
  • IAM (Dynamic Groups + Policies) — grants the OKE worker node identity scoped access to Vault secrets and the database, eliminating static cloud credentials.

K8S

Kubernetes — OKE cluster

v1.32.1 · 3 worker nodes · VCN-Native CNI · OCI Block CSI

The cluster has three worker nodes, intentionally heterogeneous in capacity:

  • 10.0.1.37 — 1 OCPU / 6 GB RAM — application workloads.
  • 10.0.1.66 — 1 OCPU / 6 GB RAM — application workloads, paired with .37 through pod anti-affinity for HA during rolling updates.
  • 10.0.1.135 — 2 OCPU / 12 GB RAM — reserved for the observability stack (Prometheus, Grafana, Loki), which will be deployed in a future iteration.

The asymmetric split provides one larger node sized for memory-heavy observability workloads while keeping two smaller application nodes whose loss is absorbed by anti-affinity-spread replicas.

The restricted Pod Security Standard is enforced per namespace. All workloads run as non-root, drop all Linux capabilities, use the RuntimeDefault seccomp profile, and mount a read-only root filesystem where the application permits.

INGRESS

Networking and ingress

Envoy Gateway · Kubernetes Gateway API · ClusterIP only

The cluster has no public IP address and no inbound firewall openings. There is no public load balancer attached to any Service. All ingress is delivered through outbound Cloudflare Tunnel connections — see the Cloudflare section.

Inside the cluster, Envoy Gateway 1.x implements the standard Kubernetes Gateway API. An EnvoyProxy custom resource explicitly pins the data-plane Service type to ClusterIP, overriding the default LoadBalancer behaviour. A single Gateway resource exposes one HTTP listener on port 80; allowedRoutes.namespaces.from: All permits HTTPRoute resources from any application namespace to attach without ReferenceGrants.

Hostname-based routing:

  • 1ms.my → urlshortener namespace (writer, reader, frontend Services selected by path)
  • cv.1ms.my → cv namespace (cv-frontend)
  • infra.1ms.my → infra namespace (this page)
Gateway + HTTPRoute (real manifests from personal-k8s) 
# infrastructure/envoy-gateway/gateway.yaml
---
# Single Gateway for the whole homelab cluster. All apps attach via HTTPRoute.
#
# HTTP-only and not HTTPS:
# Cloudflare terminates TLS at the edge (Universal SSL, free).
# Cloudflare Tunnel carries plain HTTP from edge → cloudflared pod → here.
# No reason to do TLS twice; Cloudflare↔origin link is already private
# (outbound-only tunnel, never exposed to internet).
#
# allowedRoutes.namespaces.from: All:
# each app lives in its own namespace (urlshortener, future cv, portfolio).
# they all need to attach HTTPRoute to this single Gateway.
# for tighter security later, switch to "Selector" + label-match.
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: homelab-gateway
  namespace: envoy-gateway-system
spec:
  gatewayClassName: eg
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: All
        kinds:
          - kind: HTTPRoute

# applications/urlshortener/httproute.yaml
---
# Routing rules (Gateway API matches by specificity, not array order):
#   /shorten, /createcustom  → writer service (writer ignores GET via mode flag)
#   /<6-char base62 code>     → reader service (regex by length excludes longer paths)
#   /, /*.ico, /*.webp, ...   → frontend service (catch-all)
#
# Removed `method: POST` matching because it requires experimental feature flag
# in Envoy Gateway 1.2.x. Path uniqueness alone is sufficient: frontend nginx
# doesn't serve /shorten or /createcustom, and the 6-char regex won't match
# longer asset paths like /websitebanner.webp.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: urlshortener
  namespace: urlshortener
spec:
  parentRefs:
    - name: homelab-gateway
      namespace: envoy-gateway-system
      sectionName: http
  hostnames:
    - "1ms.my"
  rules:
    # Writer endpoints — exact paths, any method.
    # Writer handler only registers POST, so a stray GET would 404 from the
    # backend itself, but that's fine — same effect as method-level routing.
    - matches:
        - path:
            type: Exact
            value: /shorten
        - path:
            type: Exact
            value: /createcustom
      backendRefs:
        - name: urlshortener-writer
          port: 80

    # Reader endpoint — short codes are exactly 6 base62 chars.
    # The $ anchor prevents matching paths with extensions or longer segments.
    - matches:
        - path:
            type: RegularExpression
            value: "^/[a-zA-Z0-9]{6}$"
      backendRefs:
        - name: urlshortener-reader
          port: 80

    # Catch-all — frontend serves "/" and static assets.
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: urlshortener-frontend
          port: 80
CLOUDFLARE

DNS, edge and tunnel — Cloudflare

Domain on Dynadot · DNS & proxy on Cloudflare · 4 tunnel connectors
  • Registrar — the 1ms.my domain is registered with Dynadot. The Dynadot domain has its nameservers delegated to Cloudflare, so Cloudflare hosts the authoritative DNS zone.
  • DNS — zone 1ms.my on Cloudflare. Each subdomain (apex, cv, infra) is a CNAME pointing at the homelab tunnel. Cloudflare creates these records automatically when public hostnames are added to the tunnel.
  • Proxy (orange-cloud) — all traffic terminates TLS at Cloudflare's edge. This provides automatic TLS certificates, DDoS protection, edge caching of static assets, and HTTP analytics.
  • Cloudflare Tunnel — cloudflared runs as a 2-replica Deployment inside the cluster and establishes outbound TLS connections to Cloudflare's edge. The tunnel currently reports HEALTHY with 4 connectors across Tel Aviv and Marseille edge POPs.
  • Tunnel hostnames route each domain to the in-cluster Envoy data-plane Service over HTTP. The cluster never accepts unsolicited inbound traffic from the public internet.

  name: cloudflared-tunnel-token
  namespace: cloudflare

  secretStoreRef:
    name: oci-vault
    kind: ClusterSecretStore
  target:
    name: cloudflared-tunnel-token
    creationPolicy: Owner
  data:
    - secretKey: token
      remoteRef:
        # Name of the secret in OCI Vault
        key: cloudflared-tunnel-token

# infrastructure/cloudflared/deployment.yaml
---
# cloudflared = the agent that makes the outbound-only connection to
# Cloudflare edge and proxies inbound traffic back into the cluster.
#
# 2 replicas for HA — one can be drained for node maintenance without
# downtime. They both connect to the SAME tunnel (Cloudflare load-balances
# automatically across all connected cloudflared instances of one tunnel).
#
# TUNNEL_TOKEN comes from the k8s Secret which ESO created from OCI Vault.
# No token in this manifest, no token in git.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloudflared
  namespace: cloudflare
  labels:
    app: cloudflared
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cloudflared
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: cloudflared
    spec:
      # Spread replicas across nodes so a single node failure doesn't
      # take down both connectors. preferredDuringScheduling so it doesn't
      # block scheduling if only one node has capacity.
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname
                labelSelector:
                  matchLabels:
                    app: cloudflared
      containers:
        - name: cloudflared
          image: cloudflare/cloudflared:2024.10.0
          args:
            - tunnel
            - --no-autoupdate
            - --metrics
            - 0.0.0.0:2000
            - run
          env:
            - name: TUNNEL_TOKEN
              valueFrom:
                secretKeyRef:
                  name: cloudflared-tunnel-token
                  key: token
          ports:
            - name: metrics
              containerPort: 2000
              protocol: TCP
          # /ready endpoint is built into cloudflared on the metrics port.
          # Returns 200 only when at least one tunnel connection is healthy.
          livenessProbe:
            httpGet:
              path: /ready
              port: 2000
            initialDelaySeconds: 10
            periodSeconds: 30
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /ready
              port: 2000
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            requests:
              cpu: 25m
              memory: 64Mi
            limits:
              memory: 128Mi
          securityContext:
            runAsNonRoot: true
            runAsUser: 65532
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
FLUX

GitOps — Flux

Flux v2.6.4 · 6 controllers · Image Automation closes the loop

The cluster's desired state is declared entirely in the AaronShemtov/personal-k8s repository. Flux reconciles the cluster against this repository every minute. The repository is the single source of truth — there is no production change that is not first a Git commit.

Six Flux controllers run in the flux-system namespace:

  • source-controller — pulls Git, OCI and Helm sources.
  • kustomize-controller — applies Kustomize overlays.
  • helm-controller — reconciles HelmReleases.
  • notification-controller — emits alerts and receives webhooks.
  • image-reflector-controller — scans container registries for new tags.
  • image-automation-controller — commits image tag updates back to Git.

Two root Kustomizations layer the cluster:

  • infrastructure — applies everything under ./infrastructure/ (Gateway API CRDs, Envoy Gateway, External Secrets Operator, cloudflared, image-automation, metrics-server).
  • applications — applies everything under ./applications/ (urlshortener, cv, infra). Depends on infrastructure being reconciled first.

The Git connection uses SSH with a write-enabled deploy key. The same key Flux uses to pull manifests is reused to push image tag updates produced by the Image Automation pipeline.

CI/CD

CI/CD pipeline — closed-loop GitOps

GitHub Actions → OCIR → Flux Image Automation → cluster

A push to any service repository propagates to running pods automatically. The diagram below shows the full loop:

Why GitHub Actions: it integrates directly with the source repository, provides build caches per repo, and runs at no additional cost on this scale. The OCI Ampere A1 compute pool is fully allocated to the OKE worker nodes, so an in-tenancy CI runner is not an option here.

Builds target linux/arm64 only, matching the Ampere A1 worker node architecture. The build itself runs natively on the GitHub-hosted amd64 runner; only the binary is cross-compiled via docker buildx. This avoids QEMU emulation entirely.

The four private OCIR repositories holding the images:

GitHub Actions workflow — urlshortener-backend/.github/workflows/build-and-push.yml 
name: build-and-push

on:
  push:
    branches: [main]
  workflow_dispatch:

concurrency:
  group: build-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build-push:
    runs-on: ubuntu-latest

    permissions:
      contents: read

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to OCIR
        uses: docker/login-action@v3
        with:
          registry: il-jerusalem-1.ocir.io
          username: axiwhc5fgu9i/shemtov.aaron@gmail.com
          password: ${{ secrets.OCIR_AUTH_TOKEN }}

      # We tag the image three ways:
      #   - 0.0.<run_number> — auto-incrementing semver used by Flux ImagePolicy.
      #     github.run_number monotonically increases per workflow file, so each
      #     successful build gets a strictly higher version than the previous.
      #   - <short-sha>       — immutable for traceability / ad-hoc rollback.
      #   - latest            — convenience for ad-hoc pulls; never used in k8s.
      - name: Resolve image tags
        id: tag
        run: |
          echo "sha=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"
          echo "ver=0.0.${{ github.run_number }}" >> "$GITHUB_OUTPUT"

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/arm64
          push: true
          tags: |
            il-jerusalem-1.ocir.io/axiwhc5fgu9i/urlshortener-backend:${{ steps.tag.outputs.ver }}
            il-jerusalem-1.ocir.io/axiwhc5fgu9i/urlshortener-backend:${{ steps.tag.outputs.sha }}
            il-jerusalem-1.ocir.io/axiwhc5fgu9i/urlshortener-backend:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Summary
        run: |
          echo "### Image pushed :rocket:" >> $GITHUB_STEP_SUMMARY
          echo "" >> $GITHUB_STEP_SUMMARY
          echo "- Version tag (used by Flux): \`${{ steps.tag.outputs.ver }}\`" >> $GITHUB_STEP_SUMMARY
          echo "- SHA tag (traceability):     \`${{ steps.tag.outputs.sha }}\`" >> $GITHUB_STEP_SUMMARY
          echo "- Convenience tag:            \`latest\`" >> $GITHUB_STEP_SUMMARY

SECRETS

Secrets management

External Secrets Operator · OCI Vault · Instance Principal

External Secrets Operator (ESO) reconciles Kubernetes Secret resources from OCI Vault on a schedule. A single ClusterSecretStore named oci-vault is configured with Instance Principal authentication — the OKE worker node identity is granted Vault read access via an OCI Dynamic Group and Policy. No static cloud credentials are stored anywhere in the cluster or in Git.

Vault secrets currently in use:

  • cloudflared-tunnel-token — the token authorising the Cloudflare Tunnel.
  • ocir-auth-token — pull credentials for OCIR, materialised as a dockerconfigjson Secret in every application namespace.
  • adb-admin-password — Autonomous Database password, consumed by the writer and reader pods as the ADB_PASSWORD environment variable.

Every application namespace contains an ExternalSecret resource referencing the relevant Vault key. Rotation is performed in Vault and propagates within refreshInterval: 1h. No secret material is committed to Git at any point.

DATABASE

Data layer — Autonomous JSON Database

Managed document store · SODA REST API over HTTPS

The URL shortener persists its data in an Oracle Autonomous Database provisioned with the JSON workload type, in the same region as the cluster. The backend communicates with the database exclusively through the SODA REST API — standard HTTPS with HTTP Basic Authentication. The Go service therefore uses only the standard library's net/http; no Oracle client libraries, no mTLS wallet, no CGO. The resulting container image remains distroless, static, and non-root.

The schema is a single SODA collection named urls, with VARCHAR2 client-assigned keys (the short codes). Document shape:

{
  "long_url":   "https://...",
  "created_at": "ISO-8601 timestamp"
}
Live API — writer endpoint and the SODA REST call it makes internally 
# Create a short URL via the writer endpoint
$ curl -X POST https://1ms.my/shorten \
    -H "Content-Type: application/json" \
    -d '{"url":"https://docs.kubernetes.io/some/long/path"}'

# Response: {"short_url":"https://1ms.my/abc123","code":"abc123"}

# Resolve a short code via the reader endpoint (returns 301 redirect)
$ curl -I https://1ms.my/abc123
HTTP/2 301
location: https://docs.kubernetes.io/some/long/path

# Internally the writer pod does a SODA REST PUT to ADB (ADMIN schema):
# PUT https://<adb-host>.adb.<region>.oraclecloudapps.com/ords/admin/soda/latest/urls/abc123
# Authorization: Basic <base64(ADMIN:****)>
# Content-Type: application/json
# {"long_url":"https://docs.kubernetes.io/some/long/path","created_at":"2026-05-26T19:00:00Z"}
SHORTENER

Application architecture — URL Shortener

Writer / reader / frontend split · independent scaling

The URL shortener is intentionally split into three independent Deployments in the urlshortener namespace. The split is a deliberate design decision aligned with the read/write asymmetry of a real shortener service.

  • writer (2 replicas) — handles POST /shorten and POST /createcustom. Generates the short code, writes the document to the Autonomous Database via SODA REST PUT, and returns the short URL to the caller. Started in MODE=writer via environment variable; the writer image registers only POST handlers.
  • reader (2 replicas) — handles GET /{6-char-code}. Reads the document from the database and returns a 301 redirect to the long URL. Started in MODE=reader.
  • frontend (2 nginx replicas) — serves the static single-page application that submits requests to the writer endpoint.

Why split writer from reader? A real URL shortener serves orders of magnitude more reads than writes — a single short link can be shared on social media and receive thousands of redirects per second while the write-side load remains effectively unchanged. By running the read path as a separate Deployment, the reader can scale horizontally (Horizontal Pod Autoscaler on CPU or request-rate) without provisioning additional writer capacity. The writer retains its small, predictable footprint. The two paths can also be deployed, drained, and rolled back independently — useful when migrating the storage backend or rolling out cache changes that affect only the read side.

Why the multi-Deployment, multi-namespace, multi-repository layout overall? The platform is structured to model a microservices architecture: each user-facing capability is its own Deployment (often its own namespace and source repository), with its own image, its own CI/CD pipeline, its own resource budget, and its own scaling profile. This mirrors how real production platforms are organised.

Five public repositories · one per concern · modeled on microservices

The platform is intentionally split across five public repositories rather than a single monorepo. Each repository owns one concern: it has its own CI/CD workflow, its own container image, and is rolled out independently by Flux Image Automation. This structure deliberately models a real microservices platform, where each service team owns a repository and the platform team owns the GitOps cluster repository.

Design decisions

Why these choices, and the alternatives rejected.

Platform & networking

  • Cloudflare Tunnel instead of an OCI Load Balancereliminates inbound public IPs entirely. TLS termination, DDoS protection and edge caching are handled by Cloudflare. The cluster has no exposed ports.
  • Envoy Gateway over nginx-ingressadopts the standardised Kubernetes Gateway API, which supports advanced traffic policies (rate limiting, JWT validation, external authorisation) natively.
  • Flux over Argo CDImage Automation is a first-class capability of Flux, removing the need for a separate Argo Image Updater. The operator model is simple and the Kustomization layering supports multi-tenancy without additional tooling.
  • Multi-repository, not monorepoindependent CI/CD, image-level versioning, clear ownership boundaries. Models a real microservices platform.
  • ARM64 (Ampere A1) workloads end-to-endmatches the worker node architecture, removing QEMU emulation at both build time and runtime.
  • No public ingress, no static credentialsevery external connection enters through the outbound Cloudflare Tunnel; every cloud credential is short-lived and scoped via Instance Principal.

Images, secrets & data

  • distroless/static:nonroot base for Go servicesfinal image is small, has no shell, no package manager, no libc, and runs as a non-root user by default. Reduces attack surface and image size simultaneously.
  • nginx-unprivileged for static sitesruns as UID 101, passes the restricted Pod Security Standard out of the box.
  • External Secrets Operator with OCI Vaultmanaged vault with native rotation and IAM audit; no secret material is ever committed to Git.
  • Managed Autonomous Database over in-cluster Postgresfrees the cluster's block-volume budget for the upcoming observability stack and removes operational burden (backups, upgrades, monitoring).
  • Writer / reader split for the URL shorteneraligns with the read-heavy traffic profile and enables independent scaling of the read path.
  • SODA REST instead of a native Oracle DB driverkeeps the Go service's container image distroless and CGO-free, with no client library or wallet mount.
